# Imported reward completion

The tracker imports received rewards, not merely eligibility. No raw account response or credentials are retained for this feature. Reimport after upgrading to populate newly supported claims; old normalized backups cannot reconstruct fields they never stored.

| Source | Evidence used | Tracker identity |
|---|---|---|
| Mission records (GUIDE, MAIN, SUB, OPENSERVER, ACTIVITY, RETRO) | Collected state 3 | `free:<mission id>` |
| Welfare operator from event missions | ACTIVITY mission collected (3), e.g. `51sideActivity_4` | `free:<mission id>` |
| Welfare operator from a main-story event's permanent missions | RETRO mission collected (3), e.g. Viy's `act4mainssPermanent_5` | `free:<mission id>` |
| Welfare operator from Record Restoration | `retro.trail[<retro id>][<trail reward id>]` = 1 | `free:trail:<retro id>:<trail reward id>` |
| Any welfare operator row (event missions, permanent missions, Record Restoration, an event's own data) | The operator is in the imported roster (`troop.chars`, kept as `operatorIds`; an older record: its outfits' `char_x#1`). Ticked while the roster holds it, not stored (`rosterClaimedWelfare`) | the row's own identity |
| Guide groups and long-term sign-in | Explicit received flag | `free:<group id>` |
| Monthly sign-in | Group ID plus binary received history | `free:<group id>:<day>` |
| Basic/all-player event sign-in | Activity ID plus binary received history | `free:<activity id>:<day>` |
| Login-only gift | Explicit received flag | `free:<activity id>` |
| Free level-up pack | A positive received count in `shop.GP.level.info` | `free:GP_freeL_<level>` |
| Global beginner sign-in | Received history plus the programme selected by registration date from the Global schedule | `free:<programme>:checkInData:<day>` or `chainLoginData` |
| Global beginner missions, as a programme | `mission.missionGroups[<programme id>]` = 1 (MissionGroupState Complete), read for the programme's `missionIds` (open_server_table `openServerMissionGroup`, kept in the game account map); 0 adds nothing. Read as all four collected: an inference from the schema, unconfirmed by a real veteran save | `free:<mission id>` |
| Stage first-clear Originite | COMPLETE (3); PASS (2) stays an ordinary clear | Existing chapter/event/resource identities |
| Paradox Simulation | Handbook state 3, or state 1 with a positive integer `completeTimes`; rewards arrive with the battle result | `paradox:<stageId>` |

On the Reward Tracker, a Beginner rewards row the save records as received shows ticked, locked and "Claimed in game" while the import lasts (`importClaimedBeginner`). The roster never ticks a beginner row: the older programme's 7-day sign-in gives Cliffheart, who is also in the headhunting pool, so owning her proves nothing. Other imported claims stay ordinary ticks the reader can change.

Paradox stage records live in the operator handbook, separately from `dungeon.stages`. The owner’s November 6 Global import reported four completed simulations with `state: 1` and `completeTimes: 1`, while 249 other completions used state 3. These state-1 successful-clear records count too. Unlock timestamps, attempts, missing/malformed states, and Operator Record story entries do not establish a completed Paradox reward. Dungeon first-clear Originite still requires state 3. Reimport once to populate this field in accounts saved before this mapping was supported. Manual tracker marks survive.

Rerun completion uses imported dungeon stage records before medals, welfare ownership or event completion marks. The normalized account keeps `recordedStages`, including valid uncleared records, separately from `rewardCleared`. When the event has ordinary battle records, every ordinary battle stage must have a three-star clear; an old medal cannot override partial or uncleared stages. When the event's records are absent, the existing completion fallbacks apply. Older imports can establish record presence from their cleared stages; reimport to retain uncleared records too. Explicit Pull Planner “Already cleared” choices remain manual overrides.

The copyable connection report includes a bounded Paradox summary from the latest import: state counts and numeric completion flags for Earthspirit, Jaye, La Pluma, Minimalist, Nightingale and Tomimi. It retains no account identifiers, timestamps, credentials or raw response, and never changes completion decisions. It is available with explicit `?importDiagnostics=1` opt-in on the production, Preview and local hosts; nothing is uploaded. This provides evidence for missed-clear reports without treating synthetic fixtures as proof of real-account behavior. The separate raw stage-metadata diagnostic remains Preview/local only.

`canCheckIn`, `nowIndex`, level thresholds, available-pack lists, elapsed time, and mission state 2 do not establish receipt. Missing, ambiguous, malformed or unsupported fields remain unknown. Announcement-only gifts, deleted or unrecognized welcome mail, voting/community bonuses (`CHECKIN_VS`, `pubBhvs`), welfare operators from an event's own data (milestones, exploration, investments: `free:welfare:<activity>:<operator>`) and beginner programmes without a matching regional schedule stay manually tracked. An official post that announces a client sign-in under its own title (same day-by-day item counts, opening within a day) is that sign-in, so it has no second, unimportable set of rows. A Global programme schedule is never guessed for JP/KR.

The Reward Tracker's overview lists only the welfare operators still obtainable (`obtainableWelfare`): Record Restoration rows (`source: 'trail'`), and an event's own operator while the event is open (`'event'`/`'extra'` to `endAt`, `'retro'` to `eventEndAt`). Sign-in days that give an operator stay sign-in rows. A collab event never reaches the Archives and no table marks it a collab, so its operator leaves with its event window. The Free rewards tab keeps every row for ticking.

Welfare operators are derived from the Global tables (the import's `importer/scripts/build/build-free-rewards.mjs`): `activity_table.missionData` CHAR rewards (open from the event's start to its stages' end), `mission_table` RETRO missions linked to their event by `retro_table.retroActList` (open from the event's start, no end), and `retro_table.retroTrailList` (from `trailStartTime`, no end). Every operator an event mission page features (`activityTemplateMissionStyles` ILLUST_CHAR_REWARD) must have a row or the build fails. Stage first-clear operators are the tutorial's and the first chapters', and Global event stores sell only tokens, so neither is a welfare row.

The catalogue carries historical beginner missions and sign-ins separately from its current default collection. Global accounts see the programme selected by registration date in both Reward Tracker and Pull Planner totals. Unknown or JP/KR registration schedules retain the default manual view. Historical receipts are never relabelled as the newer selector reward.

Reimport replaces only marks attributed to previous imports, preserving manual stage/event/free-reward decisions. Partial snapshots retain prior verified claims. Switching to a demonstrably different account drops prior automatic marks while keeping manual ones. Existing progress without provenance is conservatively treated as manual. Manual changes after an import remain in control until another import reapplies verified claims.

The **New Doctor Orundum mail** row is the one-time 3,800 Orundum starter supply. A manual Global import reads `mail/getMetaInfoList` and bounded batches from `mail/listMailBox`, through the existing encrypted browser transport. It never calls a receive, delete or mark-read route. Matching requires the specific newbie resupply subject and exactly 3,800 Orundum as its attachment; duplicate, malformed or unrelated mail stays unknown. Mail state 1 means received, 0 means unreceived. Only the matched tracker claim is retained; no mail subject, content, sender, recipient, identifier or timestamps are stored or copied into diagnostics. The diagnostic adds only read availability, retained-message count and matched claim status. JP/KR are not guessed from the English subject.

Deleted, expired or unavailable mail stays under **Needs confirmation**, manually claimable and excluded from totals. A previously verified claim survives a later import with missing mail. Explicitly unreceived retained mail contributes 3,800 Orundum until claimed; a verified received mail checks off and locks the existing row, without adding a duplicate. A failed optional read preserves the account and ends the replay continuation instead of guessing the authenticated request sequence. The full-uncompleted presentation includes the gift without changing saved completion.

Paradox availability uses the handbook stage's AWAKE promotion and level requirement against the imported `operatorBuilds` snapshot (keyed by operator name). Availability only orders and dims rows; it never establishes a claimed reward. Lower-rarity E0/E1 unlocks are preserved. Remaining sanity sums one successful clear per unfinished reward stage, after exclusions and imported/manual clears, using the compiled stage costs; retries, farming and other unlock costs are excluded. Unknown costs yield an unavailable total rather than zero.

The welfare overview's optional recommendation order follows the four tiers supplied by the owner from [kukkikaze’s guide](https://www.youtube.com/watch?v=TRb4_fCVyhk). Unlisted operators stay unranked; availability order remains selectable. These recommendations never alter eligibility or account completion.
